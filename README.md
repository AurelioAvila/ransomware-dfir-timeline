# Ransomware DFIR Timeline — SOC Home Lab

A Tier 1 SOC / Incident Responder workflow for digital forensics: correlating
multiple independent endpoint artifact sources (process creation, Prefetch,
Registry persistence, filesystem activity) into a single, MITRE-mapped
timeline of a ransomware incident, from the initial phishing attachment to
mass file encryption.

> **Note:** This is a home-lab portfolio project. All artifacts are
> synthetically generated by `generate_artifacts.py` to model a realistic
> Windows endpoint compromise — they are not collected from a real incident.
> See [`incident_report.md`](incident_report.md) for the full analyst write-up.

---

## Scenario

A file server administrator reports a burst of `.locked` files appearing on
a shared drive. No EDR alert fired. The analyst's job is to reconstruct what
happened on the source endpoint, in what order, using whatever artifacts
are available — not just the one log source that happened to be open.

## Why multi-source correlation

A single artifact source tells an incomplete story. Process logs show *what
ran*, but not whether it persisted. Registry shows persistence, but not
execution. Prefetch confirms execution count and timing, independent of
whether the logs were tampered with. Filesystem activity shows the actual
blast radius. Real DFIR work is stitching these together into one timeline
— that is the skill this project demonstrates.

## Workflow

1. Generate synthetic endpoint artifacts across 4 sources
2. Parse and normalize each source into a common timeline format
3. Apply detection heuristics to flag attack-relevant entries against MITRE ATT&CK
4. Correlate by timestamp into one unified, human-readable timeline
5. Render a report with verdict, technique summary, and execution evidence

## Setup

```bash
git clone https://github.com/AurelioAvila/ransomware-dfir-timeline.git
cd ransomware-dfir-timeline
```

No dependencies to install — standard library only.

### Run the full analysis

```bash
python generate_artifacts.py
python timeline_builder.py
```

This regenerates the artifact sources under `artifacts/`, then builds and
prints the unified timeline, writing `timeline_report.txt` and
`timeline.csv`.

### Reproducible runs

```bash
python generate_artifacts.py --seed 7
```

The filesystem-activity burst uses randomized timing/paths for realism;
pass `--seed` for a reproducible artifact set.

## Detection Logic

**Initial access / execution:**
- Office application (`WINWORD.EXE`, `EXCEL.EXE`, ...) spawning a shell interpreter (`powershell.exe`, `cmd.exe`, `wscript.exe`, `mshta.exe`) is flagged unconditionally — this parent/child pair has almost no legitimate use case
- An `-EncodedCommand`/`-enc` flag on that PowerShell process raises it to the spearphishing+obfuscation pairing

**Persistence:**
- Registry Run key values pointing to `%TEMP%` or `%APPDATA%` are flagged — legitimate autostart entries point to `Program Files`, not user-writable temp directories

**Impact / recovery inhibition:**
- `vssadmin.exe delete shadows` and `wbadmin.exe delete catalog` are flagged unconditionally, regardless of the calling process — these commands have essentially no benign automated use case on a workstation

**Impact / encryption:**
- Filesystem renames ending in a known ransomware extension (`.locked`, `.crypt`, `.encrypted`, `.enc`) are counted and summarized as a single burst event rather than one line per file, mirroring how a real triage report should compress noise
- Files matching common ransom-note naming patterns (`README_DECRYPT`, `DECRYPT`, `HOW_TO_RECOVER`, `RESTORE_FILES`) are flagged as the extortion-notice stage

## Limitations

- Artifacts are synthetic and internally consistent by construction — a real
  investigation has to handle missing/corrupted logs, clock skew between
  sources, and log rotation gaps that this dataset doesn't model
- Detection heuristics are pattern-based, not behavioral/ML — deliberately,
  to keep the logic auditable and explainable, the same tradeoff most SOC
  detection rules make
- No live memory or disk image analysis (e.g. Volatility) — this project
  focuses on log/metadata correlation, which is where most Tier 1/2 triage
  actually starts before deeper forensics is escalated
