# Incident Report — Ransomware Encryption Event (CORP-WKS-0412)

**Classification:** Confirmed ransomware, high severity
**Analyst:** Aurelio Avila (Tier 1 SOC / Incident Responder role simulation)
**Scope:** Single Windows 11 endpoint (`CORP-WKS-0412`), user `CORP\j.morales`, with lateral impact on a network file share

> This is a synthetic, portfolio-scale incident: the artifacts in `artifacts/` were generated by `generate_artifacts.py`, not collected from a real compromised host. The investigation steps and reasoning below are the same ones used against real endpoint telemetry (Sysmon, Prefetch, Registry, MFT/USN).

---

## 1. Detection

A file server administrator reported a burst of `.locked` files appearing on `\\FS01-CORP\Shared` shortly after 09:15. No EDR alert had fired — the encryptor binary was unsigned but not previously flagged, and Windows Defender was reachable but had not blocked the shadow-copy deletion.

## 2. Scoping

Correlated four independent artifact sources from `CORP-WKS-0412` to establish a source host and a timeline:

| Source | What it confirms |
|---|---|
| Process creation events (Sysmon/Security 4688) | Full process lineage from the initial document to the encryptor |
| Prefetch | Confirms each binary actually executed on this host, and how many times |
| Registry Run keys | Confirms a persistence mechanism was installed, not just a one-shot run |
| Filesystem / MFT activity | Confirms the blast radius: which directories and how many files |

| T+~5:00 | `README_DECRYPT.txt` dropped in every affected directory | T1491.001 — Internal Defacement (extortion notice) |

Total time from the malicious attachment being opened to the first encryption action: **2 minutes and 20 seconds.**

## 4. Root cause

- Macro execution was allowed for a document from an external sender (`Invoice_84421.docm`) — no macro-blocking policy for internet-sourced Office files (ASR rule / Group Policy gap)
- The dropped binary executed from `%TEMP%`, a location that should be non-executable by policy for standard users
- Shadow copy deletion succeeded, meaning the host had no tamper-protected/offline backup for this share

## 5. Impact

- 180 files renamed with a `.locked` extension across the user's local profile and one network share
- Local Volume Shadow Copies and the Windows Server Backup catalog deleted — no local recovery path
- Ransom note dropped in 5 directories

## 6. Containment & recovery recommendations

1. Isolate `CORP-WKS-0412` from the network immediately (already contained in this scenario — no further lateral spread observed beyond the single mapped share)
2. Disable the compromised account's share access pending password reset and MFA re-enrollment
3. Restore `\\FS01-CORP\Shared\Finance` and `\Shared\HR` from **offline/immutable backup** — local shadow copies are confirmed deleted
4. Do not pay the ransom or engage with the note; preserve it as evidence
5. Hunt across the estate for the same registry value name (`WindowsSvcHelper`) and the same C2 IP (`185.220.101.47`) on other endpoints

## 7. Detection gaps identified (for the blue team backlog)

- No alert fired on `WINWORD.EXE → powershell.exe` parent/child with `-EncodedCommand` — this exact pattern is one of the highest-confidence ransomware precursors and should be a standalone high-severity rule, not just logged
- No alert on `vssadmin.exe delete shadows` — should be an unconditional critical alert on any endpoint, not tuned out
- No baseline for "burst file rename rate per process" that would have caught the encryption stage before 180 files were affected

## 8. What I learned building this

- How to correlate independent artifact types (process, registry, filesystem, execution evidence) into one timeline instead of reading them in isolation — this is the actual skill DFIR work tests, not any single log source
- Why encoded PowerShell + Office parent process is treated as a near-unconditional detection rule in real SOC environments
- How fast the window between initial access and irreversible impact actually is in a ransomware chain — under 3 minutes here, which is why detection has to happen before the encryption stage, not during it
